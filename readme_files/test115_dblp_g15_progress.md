# Test115：DBLP g15 q1 分层进度门与完整结果

更新时间：2026-07-15。本文回答一个单独问题：**沿用当前 Test107 算法，DBLP g15 query 1 能否在 10,000 秒内完成。** Test115 不是新算法，而是为 Test107 增加的编译期分层观测目标；它只向 stderr 输出已经完成的 D/A 层统计，不改变状态、顺序、剪枝、答案或正式 `gst_test80_main`。

**后续跨询问压力门已经发现反例：q33 完整耗时 `11505.101s`。** 因此本文标题和结论始终只针对 q1；跨询问筛查、q33 完整分层结果与实验边界见 `test116_g15_variance_panel.md`。

## 1. 为什么先做分层进度门

旧 Test18 曾在 DBLP g15 query 1 观察到 D2 行接近全图稠密，并据此判断 D3 以后会发生状态爆炸。但该证据来自早期框架：当时 pair 层前的上界约为 `19.3812`，pair/single 分区后才降到 `17.7702`，也没有当前 Test107 的 permanent anchor、directed-cut 优先下界、工作量购买、root-irreducible branch、阶段上界和流式顶层。因此旧结论只能说明 Test18 的瓶颈，不能证明当前 Test107 仍然跑不动。

为避免直接盲跑，新增 `gst_test80_progress_main`。它与 `gst_test80_main` 编译同一份 `test80_anchor_progressive.cpp`，唯一额外宏 `GST_TEST80_PROGRESS` 只包围 `std::cerr` 输出。每个 D/A 层自然结束后报告 masks、values、pops、row bytes、best 和层时间；算法内部没有 wall time、数据集、固定 `g` 或进度特判。

## 2. 完整运行

运行命令为：

```powershell
.\build\Release\gst_test80_progress_main.exe `
  DBLP result_tmp_test115_g15_progress query_g15 data 1 1
```

完整结果已固化到 `result_snapshot/gates/20260715_test107_dblp_g15_q1`。编译配置为 Release/O2，空间字段为 `1ms` 采样的 query peak RSS。

## 4. 结论与边界

DBLP g15 q1 的 10,000 秒目标已经由当前 Test107 直接达到，不需要改变 permanent-anchor A 框架，也没有加入任何违反 `agent.md` 第六条的策略。对 q1 可以确认，Test107 的锚点组织、早期合法上界、容量下界和 branch basis 共同把旧框架的稠密 pair/k3 状态变成稀疏且在高层收缩的状态族；该结果不是数据集开关或固定层特判造成的。**这个结构结论不能推广到所有 g15 询问**：q33 的 D2/D3 平均行密度实际达到 `67.38%/46.15%`。

本轮没有新增论文引用。Test115 只是测量接口；算法来源、正确性与文献边界仍分别见 `test80_anchor_progressive.md`、`release_v4_method_cn.md` 和 `release_v4.md`。本结果只证明 DBLP g15 **query 1**；q33 已用实际完整运行否定“每条都低于 10,000 秒”，其结果不得再由 q1 外推。
