# Test157 冻结运行面板：贡献效果与最大可运行 `g`

更新时间：2026-07-18。本文汇总 ReleaseV6 效果门中的四类证据：公平 M0 到永久锚定 M1 的基线差分、M1 到 M3/M4 的核心贡献差分、M4/M5 的生产路线取舍，以及冻结 M5 在 GPU4GST 三图 `g=11..16` 的可运行性。**四者分别回答已知起点、候选贡献、最终调度和最大可运行档，不能相互替代，也都不是完整论文实验。** 高档面板的散列、逐档数据和删失语义单独见 `test157_m5_g11_g16_frozen.md`。

## 1. 固定协议

贡献消融使用 Twitch 与 Github 的 `query_g12.txt` 固定前 20 条，运行 M1、M2、M3、M4；M1/M3/M4 再以相反相对顺序重复一轮。所有阶段使用同一 Test80 源码和 MSVC Release `/O2 /Ob2`，只由编译期阶段宏改变机制。每个阶段在一个进程内顺序执行 20 条查询，图只加载一次；时间取 `weights.txt` 的逐询问 solver wall，空间取 query peak RSS。

M0/M1 参考同样使用两库固定前 20 条，各运行两个 M0 和两个重建后的 M1 run。M0 对全部 `g` 个组建立 `|S|<=floor(g/2)` 的 ordinary 状态并以规范三块同根终端结束；M1 固定永久组锚点。两者共用 ordinary-row 引擎、布局、闭包和基础 upper/lower bounds。

历史高档可运行性先使用 M4，在 Musae `g=13` 固定前 20 条、`g=14..16` 各固定前 5 条。生产审计冻结 M5 后，又统一运行 Musae/Twitch/Github 的 `g=11,12` 前 20 条和 `g=13..16` 前 5 条，并使用外部 1000 秒单询问 cutoff。算法内部没有 wall-time 策略分支，也没有运行全量 DBLP g13。

两次单独运行均未反转；保守地用较快 M0 除以较慢 M1，Twitch/Github 仍为 `2.854x/2.159x`。这通过了 M0/M1 基线效果子门，并证明状态域变化具有实际作用；固定 anchor 已有相关工作，不能由此主张原创。算法定义、随机对拍和低档结果见 `test157_m0_fair_reference.md`。

## 3. `g=12` 重复贡献面板

| 数据集 | 两轮 M1 | 两轮 M3 | 两轮 M4 | M1/M3 | M1/M4 | M1/M3/M4 平均 RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Twitch q1--q20 | 139.554s | 127.085s | 123.253s | 1.098x | 1.132x | 94.23 / 94.87 / 94.58 MiB |
| Github q1--q20 | 442.931s | 368.539s | 343.151s | 1.202x | 1.291x | 132.65 / 130.92 / 125.38 MiB |

M3 对 M1 的两轮总时间倍率在 Twitch 为 `1.099x/1.097x`，在 Github 为 `1.281x/1.120x`；逐询问胜数分别为 `12/20、13/20、20/20、16/20`。两库、两种顺序均没有方向反转，因此 **`F/H + transposed terminal` 通过当前内部时间效果子门。** M2 在只运行的一轮中分别比 M1 慢 `4.5%` 和 `1.5%`，说明不能把 `F/H` 单独宣传为稳定加速。

M4 的额外通用剪枝在两轮合计上继续改善总时间，但 Github 单轮的 M3/M4 曾为 `0.982x`，所以不能把 M4 的每个辅助模块都写成稳定增益，更不能把它们并入核心新颖性。实际 RSS 也没有统一方向：Twitch 的 M3 略高于 M1，Github 的 M3/M4 较低。详细阶段时间、胜负数和状态／事件计数见 `test157_same_source_ablation.md`。

## 5. M5 三图 `g=11..16` 面板

冻结 M5 在三图共选定 180 条查询，完成 176 条：Musae、Twitch 均为 `60/60`，Github 为 `56/60`。唯一真实超时是 Github g16 q2；该查询超过 1000 秒后终止批处理，q3--q5 因而记为未启动。不能把未启动查询写成三次额外 timeout，也不能把截断时间混入已完成查询均值。

| 数据集 | 完成 | 已完成总时间 | 最大完成时间 | 最大已记录 RSS | 最大档状态 |
| --- | ---: | ---: | ---: | ---: | --- |
| Musae | 60/60 | 814.244s | 196.173s | 527.62 MiB | g16 为 5/5 |
| Twitch | 60/60 | 628.450s | 164.407s | 766.43 MiB | g16 为 5/5 |
| Github | 56/60 | 937.801s | 175.879s | 883.72 MiB | g16 q1 完成，q2 超时，q3--q5 未启动 |

Musae 相同 q1--q5 的 M4/M5 在 g13--16 分别为 `0.979x/1.063x/1.132x/1.082x`；M5 不是逐档必胜，但 g14--16 没有出现此前担心的系统性高档回退。三图冻结面板的数据收集子门现已通过，完整逐档表、查询 SHA-256 和 cutoff 语义见 `test157_m5_g11_g16_frozen.md`。

## 6. 正确性边界

Twitch/Github `g=12` 的 80 组 M0/M1 重复比较、既有 280 个 M1--M4 阶段结果和 Musae `g=13` 的 M1--M5 权重均逐条一致。M0 另通过独立 verifier 的 1003 个检查和生产 DPBF 的 300 个随机实例。M5 又通过 1000 个生产随机实例、真实三类 row 审计和 progressive dual 独立核验。三图高档没有可在合理时间内完成的 DPBF/Strict PrunedDP++ 逐条参考，因此新面板提供的是无异常可运行性和资源证据，不是新的独立正确性证明。

## 7. 尚未完成的冻结门

1. Toronto、DBLP、DBpedia、LinkedMDB、MovieLens 的冻结多询问清单，不能以 q1 代替整档。
2. 同机 GPU4GST 作者代码对照。当前机器只有 2 GiB GeForce GT 730，无法承载作者面向 A6000 级显存的实验；该门必须在合适的 Linux/CUDA 机器完成，不能视为已通过。

M4/M5 全局取舍已经单独完成：三库 `g=4..10` 共 420 条的 M4/M5 总时间为 `212.569/207.016s`，后续冻结 M5 为唯一候选。Musae g13 q20 的 M4 小幅优势和 g14--16 q5 的 M5 优势都保留，不能概括成某一路线逐档必胜。详细协议与逐档表见 `test157_production_audit.md`。

因此完整效果门仍为**未通过**。已经通过的是“M0/M1 公平参考”“核心联合机制的内部时间效果”“M4/M5 单一路线取舍”和“GPU4GST 三图高档面板收集”四个子项；传统五库与同机 GPU 对照仍缺失。
